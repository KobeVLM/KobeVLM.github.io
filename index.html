DNS Resolution Order
2 wrong questions ▼

The exact order — memorize this

In a DNS query without caching, 4 server types work in this exact sequence:

CLIENT └──► Recursive Resolver ← receives query from client (built into OS) └──► Root Nameserver ← first step, returns TLD server address └──► TLD Nameserver ← (.com, .net) returns authoritative NS addr └──► Authoritative NS ← finally responds with the actual IP └──► BACK TO CLIENT
Most tested: "Which server receives queries from clients?" → Recursive Resolver
"Which server finally responds with the IP?" → Authoritative Nameserver
"First step in resolving a domain?" → Root Nameserver (after the recursive resolver asks it)

What each one does

Server Job Analogy
Recursive Resolver Receives query from your PC, does all the legwork You ask a librarian
Root Nameserver Points resolver to the right TLD server Librarian checks the index
TLD Nameserver Handles .com/.net/etc., points to authoritative NS Index points to a section
Authoritative NS Has the actual IP — gives the final answer The actual book with the info

SSH — the mistake you made

Wrong: sudo seankelly@chichipoo.mypup.net
Correct: ssh seankelly@chichipoo.mypup.net

SSH is NOT sudo. You use ssh user@hostname to connect to a remote server first, THEN run sudo commands on it. 
# Connect to remote server first
ssh seankelly@chichipoo.mypup.net

# Then create the user (on the remote machine now)
sudo useradd jojothepom --shell /sbin/nologin

Why /sbin/nologin?

Setting shell to /sbin/nologin prevents the user from opening an interactive terminal session. Useful for service accounts or monitoring users that only need system access, not login access. They exist in /etc/passwd but can't log in.

NTFS vs Share Permissions
Assignment Q1 ▼

Core difference

Feature NTFS Permissions Share Permissions
Applies to Local AND network users (file system level) Network users ONLY (accessing via shared folder)
Granularity Full Control, Modify, Read & Execute, List Folder, Read, Write Full Control, Change, Read only
Where set Properties → Security tab Properties → Sharing tab
Applies when Always — local or over network Only when accessed via network path

Example scenario (Assignment Q1)

Scenario: User accesses a shared folder over the network.

NTFS says: Modify (can read and write)
Share says: Read (read only)

Effective permission: Read — because the most restrictive wins.

The user can view files but cannot edit or delete them, even though NTFS would normally allow it locally.
Most Restrictive Rule
Assignment Q2 — Critical Thinking ▼

The rule

When NTFS and Share permissions are both applied, Windows uses the most restrictive combination. The effective permission is the intersection — what both allow simultaneously.

Scenario examples

NTFS Share Effective (network access)
Full Control Read Read
Modify Change Modify (both allow changes)
Read Full Control Read
Full Control Full Control Full Control

Why does this protect files? (Essay answer)

In a multi-user environment, different users may have different NTFS permissions on the same shared folder. The most restrictive rule ensures that network access never grants more than what the file system explicitly allows. For example, even if an admin accidentally sets Share to "Full Control for Everyone," the NTFS permission still acts as a safety net — a user with only Read on NTFS still can't write or delete files over the network. This defense-in-depth approach means two independent permission systems must agree before a user gets elevated access.
Explicit vs Inherited Permissions
SAM-07 slide content ▼

Explicit permissions

  • Directly assigned to a specific file or folder
  • Can be customized per individual object
  • Always takes priority over inherited permissions
  • Use when: a subfolder needs different access than its parent

Inherited permissions

  • Automatically passed down from parent folder to child objects
  • Default behavior — child inherits parent's permission set
  • Can be blocked via "Disable inheritance" button in Advanced Security Settings
Example: C:\CompanyFiles has Modify for HR group (inherited by all subfolders).
But C:\CompanyFiles\Payroll has an explicit permission: HR = Read only.
→ Even though Modify flows down from the parent, the explicit Read on Payroll wins.
Read-Only Shared Folder Setup
Assignment Q3 — Application ▼

Scenario: classmates can view but not delete

Share Permission: Read (allows viewing files over network, blocks deletion)
NTFS Permission: Read & Execute (allows opening files and running programs, no write/delete)

Why not just set Share to Read?

Share permissions only apply over the network. If a classmate ever accesses the machine locally (or if NTFS is too permissive), they could still modify files. Using both Read on Share AND Read & Execute on NTFS ensures neither path allows modification.

What "Change" on Share would allow

Share Permission Can Read Can Write Can Delete
Read ✅ ❌ ❌
Change ✅ ✅ ✅
Full Control ✅ ✅ ✅ + change perms

chmod — Understanding Permission Bits
Commands list hint ▼

Reading permission strings

-rwxr-xr-- │rwxr-xr-- │ │ │ └── Others: r-- = 4 (read only) │ │ └────── Group: r-x = 5 (read + execute) │ └────────── Owner: rwx = 7 (read + write + execute) └──────────── file type: - = file, d = directory, l = symlink Read=4 Write=2 Execute=1 Add them: rwx=7, rw-=6, r-x=5, r--=4, -wx=3, -w-=2, --x=1

chmod numeric (octal)

chmod 755 filename     # owner: rwx, group: r-x, others: r-x
chmod 644 filename     # owner: rw-, group: r--, others: r--
chmod 700 filename     # owner: rwx, group: ---, others: ---
chmod 600 filename     # owner: rw-, no one else

chmod symbolic

chmod u+x filename     # add execute for owner
chmod g-w filename     # remove write from group
chmod o=r filename     # set others to read-only
chmod a+r filename     # add read for all (u+g+o)

# u=owner, g=group, o=others, a=all
# + add, - remove, = set exactly

Common chmod values to memorize

Value Permission Use case
777 rwxrwxrwx Everyone can do anything (dangerous)
755 rwxr-xr-x Owner full, others read+execute (web dirs)
644 rw-r--r-- Owner rw, others read (standard files)
600 rw------- Only owner can read/write (SSH keys)
400 r-------- Read-only by owner (config files)
setfacl / getfacl — Access Control Lists
Commands list hint ▼

Why ACLs?

Standard Linux permissions only allow one owner and one group. ACLs let you assign permissions to specific users/groups beyond the standard three.

# View current ACL on a file
getfacl /path/to/file

# Give specific user read-only access
setfacl -m u:username:r-- /path/to/file

# Give specific group read+write
setfacl -m g:groupname:rw- /path/to/file

# Remove ACL for a user
setfacl -x u:username /path/to/file

# Remove all ACLs
setfacl -b /path/to/file

# Apply recursively to directory
setfacl -R -m u:username:r-x /path/to/dir
Scenario: You want classmate "ana" to read files in /shared without giving her group access:
setfacl -m u:ana:r-- /shared
